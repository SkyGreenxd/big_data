# Практическая работа № 2: рекомендации товаров

Реализация на Go: генератор заказов, Cross Correlation Pairs и Stripes для Hadoop Streaming и советник, самостоятельно читающий результаты из HDFS через WebHDFS. Hadoop выполняет распределение, сортировку, группировку и запуск mapper/reducer. Советник работает обычной Go-программой без MapReduce.

Обе работы входят в единый модуль `github.com/SkyGreenxd/bigdata` с `go.mod` в корне.
Из корня доступны `make build`, `make linux`, `make test` и `make demo`.

## Требования

- Go 1.23 или новее.
- Работающий Docker с Compose и поддержкой `linux/amd64`.
- Bash, Make; для локальных примеров — `sort`.
- Несколько гигабайт памяти для Hadoop; NodeManager объявляет YARN 4096 МБ для контейнеров задач, сервисам Hadoop также нужна память.

Все команды ниже выполняются из корня проекта. Порты 9870 и 9864 совпадают с первой работой: перед запуском этого кластера остановите кластер первой работы (`internal/pr1/compose.yaml`), если он запущен.

## Быстрый запуск

```bash
make test
make demo
```

`make demo` собирает программу для компьютера и Linux amd64, поднимает четыре сервиса Hadoop, ожидает готовности HDFS/YARN, генерирует данные, загружает их в HDFS и запускает два задания с двумя reducer. Затем сравнивает все частоты и рекомендации для товара «Кофе».

Каждый запуск использует новый путь `/shop/runs/<run-id>` в HDFS и каталог `internal/pr2/runs/<run-id>` на компьютере. Логи заданий, рекомендации и время выполнения сохраняются в этом локальном каталоге. Существующие результаты автоматически не удаляются.

Параметры демонстрации:

```bash
ORDERS=100000 PRODUCTS=100 REDUCERS=3 make demo
```

В демонстрации максимальный размер заказа равен 8, поэтому `PRODUCTS` должен быть не меньше 8. Для меньшего каталога используйте ручной запуск с подходящим `--max-items`.

## Ручной запуск

### Сборка и окружение

```bash
make build linux
make up
make ready
```

Интерфейсы:

- NameNode: <http://localhost:9870>.
- ResourceManager: <http://localhost:8088>.
- NodeManager: <http://localhost:8042>.

Если проверка готовности завершилась ошибкой:

```bash
docker compose -f internal/pr2/compose.yaml ps
docker compose -f internal/pr2/compose.yaml logs
```

### Генерация и загрузка

```bash
./bin/pr2 generate --orders 10000 --products 30 \
  --min-items 1 --max-items 8 --seed 42 --out internal/pr2/data
./bin/pr2 upload --src internal/pr2/data --dst /shop/input
```

Генератор создаёт `catalog.json` и `orders.jsonl`. Одинаковые параметры и `seed` дают одинаковые файлы. Существующие локальные файлы не перезаписываются; для нового набора задайте другой `--out`. Команда `upload` перезаписывает два файла в указанном каталоге HDFS.

Каталог содержит массив объектов `{"id":"p000001","name":"Кофе"}`. Первые 30 товаров имеют осмысленные названия; остальные получают названия «Товар 000031» и далее. Товары объединены в группы по пять: генератор чаще добавляет в корзину товары из группы первого выбранного товара. Это создаёт зависимости для демонстрации рекомендаций.

Заказы записываются по одному JSON-объекту на строку:

```json
{"order_id":1,"products":["p000001","p000002","p000003"]}
```

Число позиций меняется от `--min-items` до `--max-items`. Генератор создаёт уникальные товары в заказе; mapper также удаляет дубликаты при чтении сторонних данных. Заказ с одним товаром или пустым списком не даёт пар. Количество единиц товара не увеличивает частоту: один заказ добавляет каждой паре максимум 1.

### Запуск MapReduce

```bash
docker compose -f internal/pr2/compose.yaml exec -T resourcemanager bash /work/scripts/run-job.sh \
  pairs /shop/input/orders.jsonl /shop/results/pairs 2

docker compose -f internal/pr2/compose.yaml exec -T resourcemanager bash /work/scripts/run-job.sh \
  stripes /shop/input/orders.jsonl /shop/results/stripes 2
```

На вход задания передаётся именно `orders.jsonl`, чтобы каталог не попал в mapper. В каждом задании reducer используется и как combiner. Выходной каталог должен отсутствовать: для повторного запуска выбирайте новый путь. Максимальный размер входного split установлен в 1 МиБ, чтобы на достаточно большом наборе выполнялось несколько mapper.

Бинарник `bin/pr2-linux` в корне проекта собирается статически для `linux/amd64`, монтируется в контейнер подачи задания и доставляется задачам через `-files`.

### Советник и сравнение

```bash
./bin/pr2 compare --pairs /shop/results/pairs --stripes /shop/results/stripes

./bin/pr2 recommend --algorithm pairs \
  --results /shop/results/pairs --product 'Кофе'

./bin/pr2 recommend --algorithm stripes \
  --results /shop/results/stripes --product 'Кофе'
```

Без `--product` программа предлагает ввести название одной строкой. Поиск не зависит от регистра и пробелов по краям. Неоднозначное название считается ошибкой. По умолчанию выводятся до 10 товаров, отсортированных по убыванию частоты, затем по названию и ID. Можно изменить число результатов через `--limit`.

Каталог по умолчанию читается из `/shop/input/catalog.json`; другой путь задаётся через `--catalog`. Советник проверяет наличие `_SUCCESS`, получает список файлов через `LISTSTATUS` и потоково читает все файлы `part-*` через `OPEN`, включая HTTP-редирект на DataNode. Для запрошенного товара сохраняются только его соседи. Служебные файлы пропускаются.

Подключение по умолчанию: `--hdfs http://localhost:9870 --datanode http://localhost:9864 --user root`. В этом Docker-кластере DataNode сообщает внутреннее имя `datanode`; параметр `--datanode` подменяет адрес в HTTP-редиректах для работы с хоста. Для кластера с доступными клиенту адресами узлов отключите подмену через `--datanode ''`. Подмена предназначена для одного DataNode.

### Остановка

```bash
docker compose -f internal/pr2/compose.yaml down
```

Именованные тома сохраняют данные HDFS между запусками.

## Форматы результатов и алгоритмы

Используются направленные пары: совместная покупка A и B даёт вклад `(A,B)` и `(B,A)`. Частоты симметричны; это две записи для рекомендаций по каждому товару, а не удвоение частоты одной записи.

**Pairs:** mapper выдаёт компактный JSON-массив двух ID как ключ, табуляцию и 1. Reducer складывает 64-битные счётчики одинаковых ключей.

```text
["A","B"]	2
["A","C"]	2
```

**Stripes:** mapper выдаёт ID товара как ключ и JSON-словарь соседей. Reducer складывает словари по каждому соседу.

```text
A	{"B":2,"C":2}
```

В примерах между ключом и значением находится табуляция. ID должны быть непустыми и не содержать табуляций или переводов строк. Для Pairs JSON-кодирование устраняет неоднозначность составного ключа. Невалидные записи, переполнение счётчиков и несортированный вход reducer приводят к ошибке задания.

Для заказа из `k` уникальных товаров Pairs выдаёт `k*(k-1)` записей, Stripes — `k` словарей при `k > 1`. Обе схемы перечисляют все пары, поэтому выполняют квадратичное число операций по размеру корзины. Stripes уменьшает число промежуточных записей, но reducer хранит словарь всех соседей текущего товара. Размер одной входной строки ограничен 64 МиБ. Советник сканирует результаты при каждом запросе; отдельный индекс в этой работе не строится. Утилита `compare` хранит полную матрицу пар и предназначена для проверочных наборов.

## Локальная проверка без Hadoop

```bash
make build
./bin/pr2 map --algorithm pairs < internal/pr2/testdata/orders.jsonl \
  | LC_ALL=C sort | ./bin/pr2 reduce --algorithm pairs
./bin/pr2 map --algorithm stripes < internal/pr2/testdata/orders.jsonl \
  | LC_ALL=C sort | ./bin/pr2 reduce --algorithm stripes
```

Для тестового набора ожидаются шесть направленных пар: A–B и A–C имеют частоту 2 в обоих направлениях, B–C — частоту 1 в обоих направлениях. Дубликат B внутри первого заказа учитывается один раз. Это локальная проверка функций, а распределённый запуск выполняется командами Hadoop выше.

`make test` проверяет:

- известные частоты и сравнение с независимым подсчётом принадлежности товаров заказам;
- разделение входа между mapper и тремя reducer с включённым и выключенным combiner;
- воспроизводимость генератора, допустимые размеры корзин и защиту от перезаписи;
- чтение нескольких частей результатов, топ-10, равные частоты и отсутствие рекомендаций;
- повреждённые записи, переполнение и несовпадение результатов;
- WebHDFS-редиректы для чтения и загрузки, сохранение параметров запроса и ошибки HDFS;
- сборку всех пакетов единого модуля, включая первую работу.

HTTP-проверки используют транспорт в памяти и не требуют открытия портов.

## Сравнение производительности

`make demo` сохраняет время каждого задания в `internal/pr2/runs/<run-id>/elapsed-seconds.tsv`, а Hadoop-счётчики — в `pairs.log` и `stripes.log`. Для сравнения промежуточных данных используйте `Map output bytes`, `Map output records`, `Reduce shuffle bytes` и счётчики combiner. Первые два показывают выход mapper до combiner, `Reduce shuffle bytes` — объём передачи после combiner с учётом формата Hadoop.

Для воспроизводимого сравнения фиксируйте число заказов и товаров, seed, число reducer, версии Go/Hadoop и ресурсы Docker. Учитывайте прогрев JVM и порядок запуска алгоритмов; одиночное измерение включает накладные расходы запуска задания.

При реализации прошли локальные тесты, `go vet`, сборки для хоста и Linux amd64, проверка Compose и синтаксиса shell-скриптов. Docker-демонстрация и измерения на Hadoop пока не выполнены: Docker daemon в рабочем окружении недоступен.
